## 目标与当前判断

最终交付面向 Windows：作者可以用图形界面完成常规创作，也能随时修改同一份原生源码；AI 通过实际工具查询、修改、验证和预览作品；玩家获得完整的视觉小说阅读、音画、存档、历史、收藏与鉴赏体验。还须有真实插件、第二部不同风格作品、开发者文档和可复核的 Windows 交付流程。

参考渠道与语言已确定为《千恋＊万花》Steam 中文 Windows 版；具体 build、补丁和交互尚待合法实机或相应资料核验。参考事实、上游已有能力、本项目完成状态分别登记。正式美术与配音的质量、授权和最终体验也独立验收。

当前判断：工程可继续迭代，有限编辑和播放路径可用；完整 G1/G2 尚未关闭，G3—G5 仍有大块功能和验收工作。需求账本中 34 个种子 AT 均没有被授予整项通过，已有大量子项证据。不能按轮数、测试总数或补丁数量估算产品完成百分比。

## 本次复盘后的取舍

### 延续已有安全边界

继续复用原生剧本、执行器、舞台和存档，使用根仓补丁表达vendor修改。未知语法、作者注释、换行和身份保持；过期写入拒绝；错误或未应用草稿不进入活动预览。旧作品、模板备份、玩家数据及私有输入均保留。

每个源码修改单元仍需完成来源核对、失败复现、有限修复、适当回归和真实路径验证。测试组合随修改风险选择，不把所有历史测试重复相加；只有变更或未解决风险才扩展重跑范围。

### 菜单与存档采用明确策略

原需求允许菜单和历史沿用上游交互，要求明确音画是否暂停，且不能出现画面冻结但计时继续消耗的矛盾。目前记录的策略是音画继续、剧情等待菜单关闭；后续验证此策略在语音、历史试听、失焦和恢复时是否一致。若决定改为暂停，再设计同步时钟与恢复，不能把原需求误读为必须立即重写统一暂停系统。

转场期间存档要求状态一致、反馈明确、读档能恢复；最近稳定检查点和显式排队是候选策略。当前工程选择不稳定时明确拒绝并保留旧槽。继续保留这条安全底线，在完整玩家验收中评估提示与恢复操作；需要自动回退或排队时另建有取消/退出规则的单元，不借流程图修复偷偷加入玩家存档队列。现行安全策略不自动授予完整AT-11/16通过。

上述语义已同步校正需求账本N-08G/H，避免压缩摘要变成未经决定的新硬约束；具体门禁见 [舞台契约](STAGE_LIFECYCLE.md) 和 [存档说明](SAVE_COMPATIBILITY.md)。

### 由孤立样片转向完整制作链路

继续保留每个缺陷的最小复现样片，但增加一部独立的集成作品，反复用于作者编辑、人工与AI接力、双路线、保存恢复及Windows导出。它必须从正常标题开始验证玩家能力，作者跳句单独验证。多个round样片不自动算作“第二部风格不同的完整作品”。

每完成三个有界单元，回看一次集成作品和需求覆盖；若仍无法从空项目完成常规创作，优先补断点，避免只增加小控件。性能、许可与原作对标随相关能力推进，不能全部压到最后一轮。
